# Agent 动作与交互统一规范

状态：设计基线及首批候选实现，尚未部署。没有新增通用策略解析平台。
适用：已装配金融能力的标准 Agent 与 reference UI；上层 App 可以替换界面，不可绕过服务端门禁。
本规范与 [回访交付质量候选](previsit-delivery-quality.md) 同步推进，但不将文档完成视为运行策略已完成。

## 目标与职责

用户以自然语言提出目标，Agent 保持对象、任务和参数上下文。普通结果直接作为可阅读文档或标准结果组件输出；只有需要用户作出具体决定时才出现交互卡片。

| 层次 | 负责 | 不可承担 |
| --- | --- | --- |
| 业务能力合同 | 声明具体动作、读写影响、输入、敏感性、确认及审批要求 | 通过自然语言 SOP 自行豁免授权 |
| Skill / SOP | 定义业务方法、提问顺序、报告内容与证据要求 | 给模型增加未安装工具或有效权限 |
| Build / 安装准入 | 校验声明与注册工具相符，绑定动作、依赖和版本到安装证据 | 把“构建通过”当成运行时永久授权 |
| Harness | 按可信身份、实际安装合同、当前授权及平台策略作执行决定 | 相信客户端自报动作风险、用户身份或确认结果 |
| Agent Runtime | 维护待补充任务，提议动作，传递进度和结果 | 用模型输出替代服务端准入决定 |
| Assistant UI / 上层 App | 展示服务端决定、收集输入与确认，绑定当前请求 | 通过隐藏按钮或自动点击确认获得权限 |

业务资产声明必须经安装校验并绑定可信版本。资产可以要求更严格的确认，不能降低平台强制规则；平台规则可以禁止执行。未知动作性质或不完整声明不得降为普通读取。

## 统一决策规则

以下为行为规范，不是新 API 状态名。实现优先复用现有合同和事件。

| 条件 | 行为 | 用户交互 |
| --- | --- | --- |
| 未安装、不支持、无权或授权过期 | 拒绝，不调用业务 | 简短说明原因及合法下一步；确认不能解除拒绝 |
| 对象不唯一、目标或必需参数缺失 | 澄清，不执行未确定动作 | 对话追问；必要时展示获授权候选，保留已知参数 |
| 意图明确、对象唯一、授权有效的普通只读 | 直接执行，仍做运行时权限和审计检查 | 进度、结果和现有取消能力；不重复弹“确定查询吗” |
| 敏感读取、批量导出或可能显著影响隐私的动作 | 按实际合同和平台策略确认、审批或拒绝 | 不能因接口是 GET / readonly 就自动执行 |
| 转账、购买、外部发送、CRM 写入等有业务后果动作 | 授权及参数齐备后确认；需要审批则另走审批 | 展示实际对象、关键参数、影响与不可逆后果 |
| 用户明确提交内部草稿或复核意见 | 按该动作现有保存合同处理 | “保存”可构成明确提交，不机械叠加第二个弹窗 |
| 阅读或追问已保存报告 | 授权后只读该对象和版本 | 不隐式重新查询，不改写原报告 |
| 请求结果未知、连接断开或取消竞争 | 保留已知事实和准确状态，核查原请求 | 不自动重发可能有后果的业务 |

确认、授权和审批是三件不同的事。确认表达用户意图，不扩大账户范围，也不代替银行审批。只读报告中的模型建议不能直接驱动写入。

## 服务端绑定与交互

1. 先识别已安装动作和可信对象范围，再补齐参数；对话中已提供的有效信息不得反复索取。
2. 明确单客户的普通回访准备可以直接执行；产品筛选须客户、金额、期限、渠道齐备，筛选候选不等于购买或适当性批准。
3. 参数来自用户输入时仍标为待核实信息，不能把聊天内容当银行事实。名字命中不等于已有授权。
4. 确认计划在服务端绑定 actor/owner、Agent/实例代际、动作、对象、参数摘要、Lock/策略版本、授权范围、过期时间和操作标识。具体字段复用现有模型，缺口须明确补齐。
5. 参数、对象、能力或授权变化后，旧计划失效；确认消费须防重复。执行前及已有关键检查点重验授权，不能只在弹卡时检查。
6. 普通读取取消二次确认后，仍保留上述运行归属、撤权、取消和迟到隔离，不可把确认卡当作这些保护的唯一载体。
7. 卡片是对话里的决策组件，不默认弹模态窗；确认后保留回执，结果留在对应消息，不悬挂在整个会话底部。
8. 右侧“调用与证据”用业务中文说明查了什么、来源时间、结果和限制；原始标识与技术字段按需展开。必须披露的业务风险不能只藏在侧栏。
9. 手机、电脑和 ATM 展示方式可以不同，执行语义必须一致。终端适配不能暗中降低确认或授权要求。

## 首批实现与后续边界

路径均相对 integrations/customer-manager-java/src/main/java/io/github/bitlhk/finance/harness/integrations/customermanager/。

| 文件 | 当前事实 | 后续必要调整 |
| --- | --- | --- |
| ConversationIntent.java | requiresExecutionConfirmation 固定 PREPARE / PRODUCT_REVIEW | 不再用意图名直接推导所有动作的确认风险 |
| ConversationCapabilities.java | 从 Lock 读取实际安装能力，能力介绍要求用户确认 | 保留装配检查；描述与最终执行策略一致 |
| CustomerManagerScenarioExtension.java | 两动作齐备后统一 NEED_CONFIRMATION；confirmedScope 保护执行期间范围 | 普通读取可复用原 chat 执行路径，但必须独立保留 scope/epoch/取消检查 |
| ConversationConfirmation.java | 已有会话绑定、300 秒过期、一次消费及对象/能力复验 | 保留有后果动作保护，核对策略版本及参数绑定；不在前端自动 claim |
| OpenJiuwenIntentProposer.java | 提示词要求条件齐备仍确认 | 更新为提供动作提议，是否确认由可信服务端决定 |

本轮最小运行改动先覆盖经理的回访准备和产品候选筛选。其他场景沿现有合同，不因这份规范批量取消确认。推广前逐动作核对合同与副作用；确需新合同字段时采用兼容版本化，未知或旧声明保持原保守行为，不能静默自动执行。

候选通过 ConversationCapabilities.fromLock 从实际安装能力选择已核对的两项 CRM QUERY 动作。只有这两项获得直接只读执行策略；没有策略的内部调用保持原确认行为，未装配动作拒绝。这里不是对任意 QUERY 接口的普遍豁免，也还不支持上传一份新资产自动声明免确认。资产级增强确认的通用声明与准入仍是后续合同工作，不能声称本轮已经具备。

直接执行与旧确认执行复用 executeRead/chat；两者保持执行前绑定检查和 task.select 前后授权摘要检查。客户、金额、期限、渠道未齐备继续保留待补充任务。已保存版本的新查询请求仍要求切换到新对话，不在历史解释中执行。提示词及能力介绍不再强制承诺第二次确认。前端仍按服务端响应显示确认，未加入隐藏自动确认；合成经理预览同步该行为，其他场景预览保持原合同。

不新增通用调度器、企业 IAM 或第二套卡片协议；不扩展交易能力、不改变历史权限或审批政策。

## 有限验收矩阵

| ID | 输入 / 情况 | 必须验证 |
| --- | --- | --- |
| C01 | 为唯一获授权客户准备回访 | 无二次确认，单次执行；正常授权及必要审计仍执行 |
| C02 | 产品筛选缺金额、期限或渠道 | 只追问缺项，客户与任务保持，不提前调用业务 |
| C03 | 名字歧义 / 名字不在授权范围 | 安全澄清或拒绝，不披露其他 owner 对象 |
| C04 | 撤权、过期、对象/实例代际变化 | 执行检查拒绝，迟到结果不覆盖新任务 |
| C05 | 已有转账/写入/发送动作 | 原确认与审批规则不降低，不把筛选当购买 |
| C06 | 伪造确认、篡改参数、过期、重复提交 | 拒绝或复用已知回执，不重复业务执行 |
| C07 | 缺失 / 未知动作声明，模型自称已授权 | 不自动执行，不允许 SOP 绕过门禁 |
| C08 | 历史追问后提出另一个客户的新任务 | 旧报告不变，新任务绑定明确，不复用旧确认 |
| C09 | 取消与完成竞争、传输中断 | 状态准确，不删除已完成报告，不自动重发 |
| C10 | 业务意图、清晰度和终端体验 | 同一组件；只在实际决定点出现卡片；fixture 与真实 Host 验收分别记录 |
