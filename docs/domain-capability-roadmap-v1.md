# 金融能力扩展路线 V1

## 原则

新增审核、风控、保险或财富能力时，不先修改 Core。每项能力由三部分组成：

```text
Domain Pack      专业上怎么判断
Capability Pack  Agent 能调用什么标准能力
Provider         某家银行如何提供事实或执行动作
```

只有现有 `FinanceContextV1`、`CapabilityRequestV1`、`CapabilityResultV1` 和 `EvidenceReceiptV1` 无法表达真实链路时，才通过 ADR 增加 Core 原语。

## 当前已具备

| 领域 | 已有能力 | 当前证明 |
|---|---|---|
| 零售银行 | 余额查询、渠道设置、行内转账 | 查询、确认、续办和幂等 |
| 财富 | 面客资产诊断、员工访前诊断 | 同一 Core 支撑对内与对外场景 |
| 反诈 | 转账风险评估 | 外部风险系统可作为独立 Provider 接入 |
| 保险 | 员工辅助保险客户上下文与访前诊断 | 第二专业 Domain Pack 可直接装配 |

## 下一批优先级

### 1. 风险审核只读工作台

复用现有反诈 Provider 和 Evidence，补一个面向审核人员的 Domain Pack。目标是解释风险命中、列出证据和待核实项，不让大模型替代银行系统作最终放行决定。

开工前只需确认：审核岗位可见字段、现有风险接口、结果码和一组脱敏案例。若这些信息缺失，先不冻结能力参数。

### 2. 财富正式推荐

在银行或模拟环境提供当前可售及适配结果后，增加产品上下文能力与推荐 Domain Pack，验证“先组合约束、后映射 eligible products”的完整链路。适当性结论和产品状态仍来自银行系统。

### 3. 保险产品匹配

当前只读访前能力稳定后，再接正式产品、条款和报价前置条件。没有权威产品源时，只保留保障需求分析，不把培训 Demo 数据升级为正式推荐。

### 4. 审计或合规审核

先选一个真实任务，例如材料完整性核验或历史服务记录复盘，再定义对应 Pack。不要先建设通用“审核引擎”；最终处置仍由银行制度和审核岗位确认。

## 能力进入 Harness 的条件

一项能力至少满足以下条件后，才能被列为可复用资产：

1. 有清楚的业务任务和边界；
2. 有一个可运行 Provider 或稳定 Fixture；
3. 有 Domain/Capability Pack 和最小装配样例；
4. Provider Conformance 与领域案例均通过；
5. 银行可替换参数、阈值和 Provider，而无需修改 Core。

这条路线先增加可证明的业务模块，不扩建中央服务、通用规则引擎或自动 Agent 工厂。
