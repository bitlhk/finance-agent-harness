# 保险客户访前诊断

## 目标

把当前可用的客户与车辆相关事实转换成一次有目标的保障沟通，而不是直接推销产品或假设客户存在某项保障缺口。

## 工作步骤

1. 调用 `insurance_customer_context_query` 获取保险服务用途下允许使用的客户画像、字段来源、数据时间和缺失项。
2. 区分已核验事实、派生线索、待验证假设和缺失信息。画像中的标签或摘要只能作为线索，不能替代基础事实。
3. 说明为什么现在值得联系：续保节点、车辆或用途变化、保障回顾、历史异议或客户明确需求。没有可核验触发事件时，写成一般保障回顾。
4. 识别最影响后续判断的一项矛盾，例如低价诉求与责任范围、立即报价与必要信息缺失之间的冲突。
5. 将保障判断分为已确认缺口、可能缺口、不适用和无法判断；首轮最多提出三个会改变保障方向或沟通策略的问题。
6. 形成面谈目标和下一步。当前只读能力不能支持正式报价、承保、责任认定或产品推荐时，明确需要接入的业务系统或专业人员。

## 输出结构

- **本次联系重点**：触发事件和本轮目标。
- **已核验事实**：只列参与判断的事实、来源和时间。
- **保障判断**：分别列明已确认、可能和无法判断的事项。
- **首轮关键问题**：最多三个，可直接用于沟通。
- **建议沟通路径**：先确认什么，再解释什么。
- **下一步**：需要补齐的信息、业务系统核验或人工复核。

## 专业纪律

- 未返回的字段只能写“待核实”，不能推断为没有保障、没有出险或没有需求。
- 车型、职业、城市和里程不能自动推出车辆价值、事故概率、建议保额或价格。
- 不承诺最低价、一定承保、必赔、固定费率或固定服务时限。
- 责任、免责、报价、核保和理赔结论必须来自当前正式系统或条款；本 Skill 不临场补写。
- 不要求客户在对话中提供身份证号、银行卡号、验证码或完整保单号等非必要敏感信息。
- 本 Pack 只负责专业判断；客户授权、用途裁剪和数据暴露由 Runtime 与 Provider 处理。
